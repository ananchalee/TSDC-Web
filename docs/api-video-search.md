# หน้าค้นหาวิดีโอการแพ็ค + API ที่เกี่ยวข้อง

หน้าเว็บ `/video-search` — ค้นวิดีโอที่อัดไว้ตอนแพ็ค แล้วเปิดดู/ดาวน์โหลด
โค้ด: `src/app/layout/video-search/` · API: `TSDC-Api.21/API/tsdc-project/server/api.js` (ท้ายไฟล์)

## ลำดับ deploy — API → Angular (ไม่ต้องแก้ schema)

**ไม่มี ALTER** — `TSDC_VIDEO_HD.FTShop_id` **คือ** `SELLER_NO` อยู่แล้ว และ `FTCustomer_id`
ก็มีอยู่ในตาราง ทั้งคู่แค่ไม่เคยมีใครเขียน (ว่างทั้ง 771 แถว ณ 12 ก.ย. 2026)

1. deploy `api.js`
2. deploy Angular

**ของเก่าย้อนหลัง** เติมร้าน/ลูกค้าให้แถวก่อน 12 ก.ย. 2026 ได้ราว 87 แถว โดย join
`TSDC_CONTAINER_MAPORDER.SHIPMENT_ID = FTOrder_number` เอา `SELECT_NO` ลง `FTShop_id`
แล้วเปิด channel table หา `FTCustomer_id` — ที่เหลือย้อนไม่ได้เพราะตารางกลางถูกล้างไปแล้ว
⚠️ ตารางนี้ไม่มี backup ที่ใช้ได้ ถ้าจะรัน UPDATE ให้ SELECT ดูก่อนเสมอ

## ทำไมต้องเก็บ SELLER_NO ลงแถววิดีโอ

จะ join ย้อนกลับตอนค้นหาไม่ได้ เพราะตารางกลางถูกล้างเป็นรอบ — วัดกับวิดีโอ 639 แถวที่มีเลขออเดอร์:

| join ผ่าน | ติด |
|---|---|
| `TSDC_CONTAINER_MAPORDER.SHIPMENT_ID` | 87 |
| `TSDC_PICK_CHECK_NEW.SHIPMENT_ID` | 9 |
| `TMS_SHIPMENT.ShipmentID` | 0 — คนละชุด ไม่ใช่เส้นทางนี้ |

จึงต้องประทับค่าลงแถวตั้งแต่ตอนบันทึก หน้ายิงของส่งฟิลด์ `FTSeller_no` มาใน payload
(มาจาก `this.input.SELLER_NO` ซึ่งมีอยู่แล้วในหน้านั้น) แล้ว API

1. เก็บลง `TSDC_VIDEO_HD.FTShop_id` ตรงๆ
2. เปิด `TSDC_WMS_CUSTOMER_CHANNEL` ด้วยค่าเดียวกันเพื่อหา `FTCustomer_id` มาเก็บคู่กัน

> ชื่อฟิลด์ใน payload เป็น `FTSeller_no` แต่คอลัมน์ปลายทางชื่อ `FTShop_id` — ตั้งใจ
> ให้ชื่อฟิลด์ตรงกับคำที่ไลน์แพ็คเรียก (SELLER_NO) ไม่ใช่พิมพ์ผิด

**`SELLER_NO` = `FTShop_id` ของ `TSDC_WMS_CUSTOMER_CHANNEL`** (seller ที่ใช้จริง 123 ตัว match 83)
ร้านเดียวอยู่ได้หลาย channel เช่น `SHOPEE` กับ `SHOPEE_TSDC` แต่ `FTCustomer_id` ตรงกัน
API จึง `TOP 1 ... ORDER BY FNIsActive DESC, FTChannel_id` ให้ผลคงที่ทุกครั้ง

หาไม่เจอใน channel ก็ยังเก็บรหัสร้านไว้ (40 จาก 123 ร้านยังไม่ถูกลงทะเบียน) ไม่งั้นวิดีโอ
ของร้านพวกนั้นจะค้นด้วยรหัสร้านไม่เจอเลย — `FTCustomer_id` จะว่างไว้ก่อน

## `POST /search_video_hd`

ต้องมีเงื่อนไขอย่างน้อย 1 อย่าง ไม่งั้นตอบ error

```json
{
  "ORDER_NUMBER": "ICCZ143",   // LIKE 'x%' ขึ้นต้นด้วย
  "SELLER_NO":    "1148",      // ตรงตัว เทียบกับ FTShop_id
  "TRACKING_ID":  "TH5408",    // LIKE 'x%' ขึ้นต้นด้วย
  "LIMIT":        200
}
```

`LIMIT` เกิน 500 จะถูกบีบเหลือ 200

### ตั้งใจไม่มีตัวกรอง "ช่วงวันที่"

เคยมี ถอดออก 12 ก.ย. 2026 — ค้นด้วยวันอย่างเดียวลากทั้งวันมาแล้วต้องไปเช็คไฟล์บน share
ทุกแถว ยิ่งวิดีโอเยอะยิ่งหนัก และไม่ตรงกับคำถามที่คนใช้งานจริงถาม
(ถามว่า "ออเดอร์นี้อัดไว้ไหม" ไม่ได้ถามว่า "วันนี้อัดอะไรไปบ้าง")

### index และสองอย่างที่ทำให้มันไร้ผล

**สร้างบน TSDC_INTERNAL ไปแล้วเมื่อ 12 ก.ย. 2026** ไม่ต้องรันซ้ำ

| index | ใช้ตอน |
|---|---|
| `IX_TSDC_VIDEO_HD_Order` (FTOrder_number) | ค้นด้วยเลขออเดอร์ |
| `IX_TSDC_VIDEO_HD_Shop_Start` (FTShop_id, FDStartdate DESC, FNVideo_id DESC) | ค้นด้วยรหัสร้าน |
| `IX_TSDC_VIDEO_HD_Tracking` (FTTracking_id) | ค้นด้วยเลขพัสดุ |
| `IX_TSDC_WMS_CUSTOMER_CHANNEL_Shop` (FTShop_id, FNIsActive DESC, FTChannel_id) INCLUDE ชื่อร้าน | OUTER APPLY ที่ไปเอาชื่อร้าน |

**1. ห้ามเอา `OPTION (RECOMPILE)` ออก** — WHERE เป็นแบบ `(@x = '' OR คอลัมน์ ...)`
คำขอแต่ละแบบต้องการ index คนละตัว แต่ SQL คอมไพล์ plan จากคำขอแรกแล้วใช้ซ้ำกับทุกคำขอ
ดู plan จริง: ไม่มี RECOMPILE → ค้นด้วยรหัสร้าน/เลขพัสดุกลายเป็น **Index Scan ของ
`IX_..._Order`** คือไล่ index ผิดตัว ไม่ได้ใช้ของตัวเองเลย

**2. ต้องใช้ `LIKE 'x%'` ไม่ใช่ `'%x%'`** — แบบมี `%` นำหน้า SQL seek ไม่ได้ ต้องสแกนเสมอ

> plan เปลี่ยนตามความเจาะจงของคำค้น ซึ่งถูกต้อง — `TH54` ได้ Index Seek ส่วน `TH`
> เฉยๆ เลือกสแกนเพราะที่ 771 แถวมันถูกกว่า `RECOMPILE` คือตัวที่ให้สิทธิ์เลือกรายครั้ง

`IX_TSDC_WMS_CUSTOMER_CHANNEL_Shop` อยู่บนตาราง master ที่ระบบอื่นใช้ร่วมกัน — เป็นการ
**เพิ่ม** อย่างเดียว ไม่แตะโครงสร้างหรือข้อมูลเดิม ทำให้ OUTER APPLY เปลี่ยนจาก
`Clustered Index Scan + Sort` (ทำซ้ำทุกแถวผลลัพธ์) เป็น `Index Seek` ตัวเดียว
ส่วนเกินของ APPLY ลดจาก ~4.2 ms เหลือ ~2.0 ms ต่อการค้น 200 แถว

### Response

```json
{
  "status": "success",
  "count": 12,
  "truncated": false,
  "data": [ { "FNVideo_id": 661, "FILE_STATUS": "ready", "CAN_PLAY": true, ... } ]
}
```

`truncated: true` = ผลชนเพดานพอดี อาจมีมากกว่านี้ หน้าเว็บจะเตือนให้กรองแคบลง

### `FILE_STATUS` — API ไป `fs.statSync` ไฟล์จริงให้ทีละแถว

| ค่า | แปลว่า |
|---|---|
| `ready` | ไฟล์อยู่บน server เปิดดู/ดาวน์โหลดได้ |
| `missing` | DB มีพาธ แต่ไฟล์ถูกลบไปแล้ว |
| `not_ready` | `FTPath_server` ว่าง ยังไม่เคยขึ้น server |
| `recording` | `FNStaUpload = 2` ยังอัดไม่จบ |
| `no_access` | API เข้า share ไม่ได้ (สิทธิ์/เน็ตเวิร์ก) |

**`no_access` ต้องแยกจาก `missing` ให้ได้** ไม่งั้นวันที่สิทธิ์ share หลุด หน้าเว็บจะรายงานว่า
"ไฟล์หายทั้งหมด" ทั้งที่ไฟล์อยู่ครบ โค้ดจึงดู `e.code === 'ENOENT'` ไม่ใช่ดักทุก exception รวมกัน

### ⚠️ ห้ามกลับไปใช้ `fs.statSync` วนทีละแถว

วัดบน share จริง 12 ก.ย. 2026:

| | 200 ไฟล์ |
|---|---|
| ไฟล์ **มีอยู่จริง** — เรียงทีละตัว (`statSync`) | **1,296 ms** |
| ไฟล์ **มีอยู่จริง** — ยิงพร้อมกัน 8 ตัว | 306 ms |
| ไฟล์ **ถูกลบไปแล้ว** — เรียงทีละตัว | 6 ms |

ไฟล์ที่หายเช็คเร็วมากเพราะไม่ต้องคุยกับ share จริง และตอนนี้ในตารางเป็นแบบนั้นเกือบหมด
(402 แถวมีพาธ เปิดได้จริง 15) **หน้าเว็บจึงดูเร็วอยู่เพราะไฟล์หาย ไม่ใช่เพราะโค้ดดี**
พอ uploader เริ่มทำงานไฟล์มีจริงขึ้นมา แบบ `statSync` จะช้าลงทันทีเป็นวินาที

เพิ่มเกิน 8 ไม่ได้อะไรแล้ว — 8/16/32/64/200 ตัว ได้ 306/311/297/305/295 ms
คือชนเพดานของ share ไม่ใช่ของเรา จึงหยุดที่ 8 เพื่อไม่ถล่ม share (`STAT_CONCURRENCY`)

> ถ้าเจอ `no_access` ทั้งหน้า แปลว่า account ที่รัน API บน 10.26.1.21 เข้า
> `\\10.26.1.26\Dev\Video` ไม่ได้ — ต้องให้สิทธิ์ share กับ account นั้น ไม่ใช่แก้โค้ด

## `GET /video_hd_file/:id`

ส่งตัวไฟล์ · `?download=1` = แนบ `Content-Disposition: attachment` ให้เบราว์เซอร์เซฟลงเครื่อง

พาธเอามาจากแถวใน DB เท่านั้น ไม่เคยรับพาธจากผู้ใช้

**รองรับ `Range`** ซึ่งจำเป็น ไม่ใช่ของแถม — ถ้าไม่ตอบ `Accept-Ranges` เบราว์เซอร์จะโหลด
ทั้งไฟล์ก่อนถึงจะเล่นได้ และลากแถบเวลาไม่ได้เลย ซึ่งใช้ไม่ได้กับคลิปหลักร้อย MB

ฝั่ง Angular จึงใส่ URL ลง `<video src>` กับปุ่มดาวน์โหลดตรงๆ **ไม่ดึงผ่าน HttpClient เป็น blob**
เพราะ blob จะกินแรมเท่าขนาดคลิปทั้งก้อนและเสียความสามารถ seek

| กรณี | ตอบ |
|---|---|
| ไม่มีแถว id นี้ | 404 |
| `FTPath_server` ว่าง | 404 `ยังไม่ถูกอัปโหลดขึ้น server` |
| ไฟล์ถูกลบ (ENOENT) | 404 `ไฟล์ถูกลบไปจาก server แล้ว` |
| เข้า share ไม่ได้ | 502 พร้อม error code |
| ขอ Range เกินขนาดไฟล์ | 416 |

## หน้าเว็บ

จัดกลุ่มผลตาม **เลขออเดอร์** เพราะคนค้นคิดเป็นออเดอร์ ไม่ใช่ไฟล์
ออเดอร์เดียวมีหลายคลิปได้ 2 แบบ: อัดยาวเกินถูกตัดเป็น segment และออเดอร์เดิมที่เอามาเช็คใหม่

- กลุ่มเรียงใหม่สุดอยู่บน · **ในกลุ่มเรียงเก่าไปใหม่** เพราะ segment 001 → 002 คือลำดับการเล่น
- ข้อมูลระดับออเดอร์ (ร้าน/tracking/โต๊ะ) หยิบ "ค่าแรกที่ไม่ว่างจากทั้งกลุ่ม" ไม่ใช่จากแถวแรก
  เพราะบางแถวว่างได้ เช่น tracking ที่เพิ่งถูกเลือกหลังเริ่มอัดไปแล้ว
- จอเล่นวิดีโอทำเป็น overlay เอง ไม่ใช้ modal ของ bootstrap จะได้ไม่ต้องพึ่ง jQuery
  และคุมจังหวะ `pause()` + ล้าง `src` ตอนปิดได้แน่นอน ไม่งั้นเสียงเล่นต่อหลังปิดจอ

### ⚠️ เวลาต้องอ่านด้วย `getUTC*` เท่านั้น

คอลัมน์เป็น `datetime` ของ SQL ซึ่งเก็บ "เวลาหน้าปัด" ไม่มี timezone แต่ driver คืนมาเป็น ISO
ที่ลงท้าย `Z` เช่น `2026-08-15T15:54:52.000Z` — ค่าจริงคือ 15:54:52 ตามเวลาไทย
ยืนยันได้จากชื่อไฟล์แถวเดียวกันที่ลงท้าย `Time(15-54-52)`

ถ้าอ่านด้วย `getHours()` เบราว์เซอร์บวก +7 ให้ทันทีกลายเป็น 22:54
`video-search.component.ts` จึงมี `parts()` ที่ใช้ `getUTC*` ตัวเดียวสำหรับทุกการแสดงเวลา
